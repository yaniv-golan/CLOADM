# The HD6309 core and its sources

[CLOADM](../README.md) › The HD6309 core and its sources

The 6309 machines (`cocoh`, `coco3h`, `dragon64h`, `tanodr64h`) run `js/cpu/cpu6309.js`, the 6809 core plus the
6309's registers, instructions, native mode and traps. Its cycles, flag rules and result registers are taken from
the sources below, and the product default is what they say. MAME 0.289 differs from them in places; those
differences are reproduced only under `config.mameCompat`, so a lockstep comparison can run strict (no allowed
differences, in `tools/mame-diff/lib/lockstep.js`), and the table is `MAME_DELTA` in the core.

**The sources, by the titles on the documents:**

* **Hitachi**, *8/16-BIT MICROPROCESSOR DATA BOOK*, Hitachi America, #U70-B, August 1987. Table 9 "HD6309E
  Instruction Set Table" (pp. 302-...) is the vendor's opcode table. It tabulates only the instructions the 6309
  shares with the 6809: it has no row for MULD, DIVD, DIVQ, SEXW, LDQ, STQ, LDMD, BITMD, ANYD/ORD/EORD, the
  inter-register ops, BAND..STBT or PULSW/PULUW. "Hitachi silent" below means the vendor table
  lists no figure for the instruction, so it cannot settle a dispute about one.
* **Darren Atkinson**, *Motorola 6809 and Hitachi 6309 Programmer's Reference*, 2009. The only source found that
  states cycle counts, flag rules and result registers consistently for every 6309 instruction, in both modes;
  it is a secondary, reverse-engineering reference. Its per-instruction pages give the figures used here, and
  its programming aid (the instruction table) repeats them.
* **"Sock's Accelerated 6309 CPU Cycle Charts"** (6809.org.uk/twilight/sock), which prints explicit
  emulation / native / accelerated columns. Lindner's addendum cites it.
* **Chet Simpson and Alan DeKok**, *HD63B09EP Technical Reference Guide*, 1994: registers, modes, the instruction
  descriptions and an opcode table with `( )` native-mode figures. The "guide" below.
* **Tim Lindner**, *Addendum to The 6309 Book*, 2003: the indexed post-byte cycle tables, A-12a..d, with separate
  emulation and native columns.
* **MAME 0.289**, `src/devices/cpu/m6809/` (`hd6309.cpp`, `hd6309.lst`, `base6x09.lst`, `m6809inl.h`): the
  reference for `config.mameCompat` only, and the version the comparison must be run on.

Two figures in the sources are self-contradicting rather than disputed, and are noted in the code and the tests:
Sock's ADCB extended row above, and the guide's DIVD prose ("quotient in W and the modulo in D", which is the
DIVQ rule). One figure is contested and resolved to the majority: DIVQ's immediate count, 34 (Sock, Atkinson,
which Lindner's addendum cites) against the guide's 36.

**What the compat path changes, and the one question it leaves open.** `MAME_DELTA` holds the measured cycle
differences only. The flag differences reproduced under `mameCompat` are three: DEC/DECW and INC/INCW set C from
the borrow or carry (the hardware leaves it alone), ROLW's V is always clear (the hardware sets bit14 XOR bit15),
and LDMD replaces the whole MD byte and sets N/Z/V (the hardware keeps bits 2-7 and changes no flag). Four flag
rules are *not* differences, and both modes implement them the same way: LSRW, TSTW (V cleared on both, see the
table), CLRW, and the illegal-instruction and divide-by-zero trap.
The trap's CC behaviour is the one rule no source states: Atkinson p. 59 says only that the trap "sets bit 7 in
the MD register, stack[s] the machine state and jump[s] … at `$FFF0`", the guide says the same in prose, and the
Hitachi data book has no 6309 trap section at all. MAME routes the trap through its `SOFTWARE_INTERRUPT`, the
SWI2/SWI3 path, which does not touch I or F; its `SWI` sets them separately (`base6x09.lst`). Masking both, as
RESET, NMI, FIRQ, IRQ and SWI do, is a plausible alternative, but SWI2 and SWI3 do not mask (Atkinson note 5), and
the trap is at least as close to those. With no primary source to prefer either, the product default follows MAME,
so both paths leave I and F as they were and there is no compat branch for it; a unit test pins
that from both starting states.

**How it is verified.** `node tools/mame-diff/run.js <profile> --cpu 6309` runs `tools/mame-diff/6309/sweep.asm`
(our own firmware, installed in place of the BASIC ROM) in lockstep with MAME's HD6309 driver for the profile. The
sweep runs every 6309-only instruction in every addressing mode, in emulation mode and again after `LDMD #$01`,
the four TFM variants, a divide-by-zero trap, and, in each mode, an IRQ, a FIRQ, a FIRQ with MD bit 1 set
(FIRQ-as-IRQ), CWAI and SYNC, each returning through RTI, and ends in HALT. The machine is built with
`config.mameCompat`, so the comparison is strict: every register and every cycle count must match, and
`lockstep.js` has no machinery for an exception. `tests/cpu6309.test.js`, `tests/cpu6309-timing.test.js` and
`tests/cpu.test.js` cover the same behaviour in Node, including the compat path and the interrupt frames, so the
fast gate does not need MAME.

**The TFM cases fold the destination into a register, because the lockstep never reads memory.** `lockstep.js`
compares registers and cycle counts and nothing else, so a TFM that wrote the wrong addresses while leaving the
right values in X and Y would compare identical, and did: the `3A` form walked the destination pointer instead
of parking it, and the `3B` form walked the source instead of parking it, while both ended with the correct
pointer registers. Each TFM case therefore sums the 16-byte destination window into D and stores it, so a byte
in the wrong place changes a value the comparison reads. The sweep also emits TFM as raw bytes (`FCB $11,$3A,$12`)
rather than as a mnemonic, so the core's coverage cannot be masked by an encoder bug. Both were needed: with the
fold and the bug present the lockstep diverges at instruction 2761 (MAME's D is `$1300`, ours `$1000`); without
the fold it passes.

**The interrupt cases take their sources from devices, not from MAME's debugger.** MAME 0.289's Lua exposes no
way to assert an interrupt line (`set_input_line`, `pulse_input_line` and `nmi` are absent from the debugger's
CPU object; only `ioport` is there), so the firmware drives real hardware instead, identically in both:
IRQ from PIA0 CB1 (the VDG field sync), FIRQ from PIA1 CB1 (CART, which a Program Pak ties to Q, so a PIA1
write toggles it under `mameCompat`). The IRQ uses the field sync rather than the line-rate HS pulse because a
line-rate interrupt re-fires within a few hundred cycles of the RTI, and whether it lands before or after the
instruction that re-masks is a race — the first attempt at this block lost that race and diverged. NMI is not
covered by the sweep: it is reachable only through a cartridge device (the FDC's INTRQ), and mounting one is a
separate comparison; its vector is checked here, an NMI frame is not. It is covered separately, for the Dragon
models and on both CPUs, by `--fdc --nmi` above. PIA0's port B is made an output register holding 0
first, because clearing a PIA flag takes a read of the *port*, and the port's unconnected pins do not read the
same in both emulators (MAME reads 00 on the Dragon, this core reads FF).

Two CPU figures came out of the interrupt cases and are recorded in the core:

* **CWAI.** The 6309's CWAI is 22 cycles in emulation mode and 20 in native mode [Atkinson "CWAI", printed p. 55; Sock
  "3C 22/20"; guide Table 9], and that figure includes the wait. MAME charges 16 (its `base6x09.lst CWAI`: the
  mask fetch, a dummy read, a dummy VMA and the twelve pushes) and then 4 for the vector fetch on the next step,
  doing none of the idle time. Under `mameCompat` the instruction is MAME's 16 with no wait charged here. This
  cannot be an ordinary `MAME_DELTA` entry: the difference is 4 internal cycles plus 2 that were never logged,
  and `dropInternal()` can only take away cycles that are in the log, so `cwai6309()` handles it.
* **SYNC.** MAME's SYNC ends its wait with `@eat(1)` whether or not an interrupt is taken; an interrupt taken
  out of a SYNC therefore costs one cycle more than one that only releases the wait. This core was one cycle
  short on the taken path, which the sweep's SYNC case measured (MAME 17,691 cycles from the SYNC to the
  handler, ours 17,690). `checkInterrupts()` now adds that cycle.
* **The 8-bit read-modify-write family on memory, in native mode and in every memory mode.** Atkinson gives
  each of these 6/5 direct, 6+ indexed and 7/6 extended, on its own page: NEG p. 103, COM p. 54, LSR p. 98,
  ROR p. 118, ASR p. 18, ASL p. 16, ROL p. 116; DEC p. 58, INC p. 68 and CLR p. 49 are the same, and TST
  (p. 141) is 6/4 direct, 6+/5+ indexed and 7/5 extended. This core follows the table, which is the product
  default. MAME 0.289 charges one cycle less than the table in native mode, in all three memory modes, for
  NEG, COM (direct, indexed and extended alike), LSR, ROR, ASR, ASL and ROL: its figures are 4 direct,
  5 indexed and 5 extended where the table has 5, 6 and 6. It agrees with the table on DEC, INC, CLR and TST.
  There are **21 entries (7 instructions × 3 modes)** for the seven that differ, one per opcode — NEG
  `00/N` `60/N` `70/N`, COM `03/N` `63/N` `73/N` (the indexed form is `63`, which is the one cited here),
  LSR `04/N` `64/N` `74/N`, ROR `06/N` `66/N` `76/N`, ASR `07/N` `67/N` `77/N`, ASL `08/N` `68/N` `78/N`,
  ROL `09/N` `69/N` `79/N` — applied only under `config.mameCompat`; the four that agree must never get one.
  The sweep runs all **eleven instructions** in all three memory modes, so a stray entry, or a missing one on
  a differing mode, fails the lockstep immediately. `tests/cpu6309.test.js` pins both figures for all of
  them through a real machine, not a bare CPU.

The two sweep variants (16K and 32K ROM windows) are generated by `gen-sweep.js`; the CoCo 3's window is 32K, so
its vectors sit at `$FFF0` and its run uses `sweep32.asm`. **Not verified against MAME 0.264:** the table encodes
0.289, so the 6309's lockstep and its regression hashes are taken against 0.289 rather than the project's 0.264
reference. The reason is narrow and measured: **0.264 is not an oracle for the 6309's divides.** It charges
`DIVD #$02` 3 cycles where 0.289 charges 28 and Atkinson's `DIVD` page (printed p. 58) gives 25 for the immediate
form, 27/26 direct, 27+ indexed and 28/27 extended (his `DIVQ` page, printed p. 59, gives 34 immediate, 36/35
direct, 36+ indexed, 37/36 extended): its own trace shows `totalcycles` 291 → 294 across the instruction, so the
cycles are not moved to another entry, they are not charged at all. Atkinson is the default here and `mameCompat`
encodes 0.289, so 6309 firmware that divides has to be compared against 0.289, and the sweep diverges on 0.264 at
instruction 2,399 for exactly that reason, while the same firmware is identical on 0.289. (`DIVD #$00` rows are
not comparable at all: the delta spans the trap handler's own instructions, which a filtered trace does not
show.)

**In the regression gate:** two cases, `trace dragon64 6309` and `trace coco3 6309`, hash the whole sweep (every
register and cycle count for the full run), so a change to the 6309 core, its timing table or the sweep fails in
seconds without MAME. The CoCo 3 case runs the same firmware through the 32K window, so the two together cover
both vector placements.

**Three opcodes the hardware does not have, and this core runs anyway.** NEGW, ASRW and ASLW (`$1050`, `$1057`,
`$1058`) are not 6309 instructions: Atkinson's opcode map leaves those cells blank (printed p. 152) and its
instruction pages say so in as many words — "The 6309 does not provide instructions for negating the E, F, W and Q
accumulators" (NEG, printed p. 101), "does not provide a variant of ASR to operate on the W accumulator" (ASRD,
printed p. 18), "The D accumulator is the only 16-bit register for which an ASL instruction has been provided"
(ASLD, printed p. 16). Undefined opcodes trap on a 6309 (printed p. 153, note 4), so the hardware takes the Illegal
Instruction exception for all three. Our core and MAME 0.289 (its page-2 dispatch, `case 0x50`, `0x57`, `0x58`)
execute them as the W forms of NEG/ASR/ASL instead. The disassembler follows the hardware and prints them as data.
The difference is one of behaviour, not of length - the core reads the same two bytes it would need to trap - so the
disassembler's length comparison still holds for them, and the disassembler test says so; a byte-count test cannot see
the trap either way. The core change is tracked for its own branch, with the trap's vector, stacked state and cycles
to be checked against Atkinson.

**In the Debugger.** A machine with the 6309 option shows the full 6309 register set on the Debugger screen (PC A B
E F D W Q V MD X Y U S DP, with the 6809 condition codes), and its fields edit the core as a 6809's do; Q is shown
and edited as eight hex digits. Code is disassembled with the 6309's own instruction table and against the CPU's real
direct page, so LDQ and the other 6309-only opcodes read as instructions rather than data. The register tables and the
`codeDisassembly` helper live in `js/debugger.js`, so the Debugger, the trace and Ask's "What is this code doing?"
share them.
