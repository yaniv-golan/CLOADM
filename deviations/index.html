Known differences from MAME

CLOADM is compared with MAME 0.264 instruction by instruction and pixel by pixel, on firmware written for this project. Where the two differ on purpose, it is because a datasheet, a schematic or a measurement says the hardware does otherwise. Each difference is below, with its source. Where MAME's way is kept behind config.mameCompat, the comparisons turn it on, so they still match MAME exactly. This list is docs/verification.md's, word for word.

The differences

  • Playing a .CAS file (js/media/tape.js): MAME rewrites the file's leaders, making every leader in front of a namefile, and in front of the block after one, exactly 128 bytes (a longer one is shortened), adds one $55 to every block, and plays a run of $55 bytes between two blocks about four times as long (measured with tape/gaps.asm: a run of n bytes between blocks gives 4n - 3). A .CAS file is the bytes that were on the tape; we play them as they are and only make up leaders that are too short for BASIC to find the block, with MAME's silences. What a program reads is the same (tape/cloadm.asm, above); the comparison of the signal checks the silences and shows the runs between them without comparing them.
  • The Speech/Sound Pak's speech on the sound path (js/machines/ssc.js, SP_LAG): each speech sample's level is heard from two sample periods after its period starts, about 0.2 ms late. The chip makes a sample when its period ends (or, for a status read or an address load, when it starts), up to a PIC instruction after the AY's samples for the same moment have been passed on, and the machine's sound path takes levels in time order; two periods on is after the card's position whenever a sample is made. MAME's stream holds sample k for its own period. The comparison (ssc/speech-audio.js) reads our levels at those stamps, so the values are compared exactly; only the 0.2 ms differs.

MAME artefacts reproduced only under config.mameCompat (the comparisons turn it on; the product does not):

  • SP0256 sample rate (js/chips/sp0256.js, SAMPLE_CLOCKS; js/machines/ssc.js, spGrid): the hardware makes one sample every 312 clocks of its 3.12 MHz crystal, 10 kHz (GI's "SP0250 Applications Manual", June 1982, pin 20 SYNC: "640ns positive pulse with a duty cycle of 312 clocks"; the 3.12 MHz crystal from the Radio Shack SP0256 datasheet, catalog 276-1784; CPCWiki's "SP0256 Measured Timings" gives 3.12 MHz / 2 / 156 = 10 kHz, a secondary source not read here, its host being network-blocked). MAME 0.264's sp0256.cpp divides by CLOCK_DIVIDER (7*6*8), 336, with no citation, while its own comment says it generates "~10kHz samples"; as a whole-hertz stream that is 9,285 samples a second, counted from each second's start. Under config.mameCompat the chip runs on MAME's grid; otherwise at 10 kHz.
  • SP0256 LRQ and the PIC's scheduler (js/machines/ssc.js, stepCard): MAME gives a CPU the time to its next timer as a whole number of its cycles, rounded down, and does not run it for none, so the speech chip's per-sample timer fires before a PIC instruction that would start less than one card cycle earlier. Under config.mameCompat an LRQ change that close reaches INT1 before the instruction; otherwise after it, at the instruction's end. Measured with ssc/gen-speak.js: instructions starting 0.06 and 0.88 card cycles before a sample boundary read the INT1 flag set on MAME, each moving one address load by a pass of the PIC's polling loop (23 card cycles) until this was modelled.
  • Speech/Sound Pak AY sample grid (js/machines/ssc.js, mameAySamples): on the hardware the AY makes one sample per 4 card cycles (its clock is twice the card's, and a sample is 8 of its clocks). MAME keeps device clocks as whole hertz, so the Pak is 894,886 Hz (888,625 on the Dragon), the AY 1,789,772 Hz and its stream 1,789,772 / 8 = 223,721 samples a second, counted from each second's start (sound.cpp, time_to_buffer_index), where 4 card cycles would make 223,721.56. MAME's grid therefore slips about half a sample a second against the card's cycles, and a register write near a sample boundary lands one sample later than on the hardware's grid; measured with ssc/gen-ay.js, that put a tone half a period out of phase after a period change at 1.008 s. Under config.mameCompat the AY's samples fall on MAME's grid; otherwise on the hardware's (tests/ssc.test.js: 223,721 and 223,722 samples in the first 894,886 card cycles).
  • CoCo 3 GIME vertical fine scroll ($FF9C): MAME 0.264 never scrolls a GIME-mode row (its top border resets the row's line counter on every line, gime.cpp record_border_scanline, after new_frame loaded VSC into it). The sources (Sock Master's GIME reference, "FF9C Vertical scroll register - VSC"; Tepolt (1987) pp29-30; above, "CoCo 3 GIME vertical fine scroll") say VSC below the row height moves the picture up by VSC lines; the machine as shipped does that (js/chips/gime.js vscLine). What no source settles, and how we treat it, MAME-identical in every comparison: VSC at or above the row height, rows of one line ($FF98 LPR 0 and 1) and LPR 7 are not scrolled; VSC is latched at the start of the field (MAME's new_frame); 1986 and 1987 GIMEs are not told apart. Each of these is unverified on real hardware.
  • Dragon 64 Plus: MAME 0.264's $FFE2 write (d64plus_bank_w()) sets its two memory banks' entries, but CPU and VDG accesses to $0000-$7FFF keep reaching the standard RAM: a Lua probe writing each documented value and then $0100 and $1000 reads back what it wrote every time, while the :plus_ram and :video_ram shares are never written. Compusense's technical notes (above) document working banks, and MAME 0.289 banks as the notes say; 0.264 does not. A separate local probe of 0.289's $FFE2 (16 cases, none differing from js/machines/d64plus.js) found bits 2-1 select the bank, bit 0 maps the video RAM over $0000-$07FF only, and the read's bit 0 is 1 outside blanking. Both versions' d64plus_bank_w() leave both banks' entries as they were for the undocumented $04/$05 (0.264's entries after $03 then $04: plus RAM 1, video RAM 3), and so do we under mameCompat. Without mameCompat the banks reach the CPU (js/machines/d64plus.js).
  • Dragon 64 Plus, without mameCompat: $FFE2 = $04 selects the motherboard RAM ($05 the motherboard RAM with the video RAM), where MAME's d64plus_bank_w() leaves the banks as they were; and the MC6847 always fetches the motherboard RAM, where MAME's driver installs the banks in the SAM's space, through which its VDG fetches too. Source: P. Harvey-Smith's traced Eagle schematic of his DragonPlus board (World of Dragon forum, 7 June 2017, viewtopic.php?p=15826; known drawing errors): bit 2 only XORs Z7 into the extra DRAM's address, and the MC6847 reads in E = 0. Not verified on hardware. MAME 0.264 still compares (it never applies $FFE2, so its outcome is the schematic's: run.js d64plus --paging [--video], above); the 0.289 probe above was not re-run, and on $04/$05 and the VDG 0.289 is expected to differ from us.
  • A cartridge that ties CART to Q (the program pak with auto-start, the banked ROM cartridge, the Games Master, the Orchestra-90): MAME toggles the line five times through its slot's timers whenever a PIA1 register is written (cococart.cpp twiddle_q_lines, called from coco.cpp ff20_write and on the CoCo 3 from coco3_state::ff20_write, "something that approximates the cartridge Q line behavior"). On the hardware CART follows the CPU's Q clock all the time (coco_pak.cpp: "normal CoCo PAKs tie their CART line to Q - the system clock"); without mameCompat ours toggles it once per scan line, so PIA1 CB1 (and on the CoCo 3 the GIME's EI0) sees edges continuously (js/machines/sam.js lineStart, js/machines/coco3.js hsRiseEvent).
  • HALT: MAME suspends its 6809 at the scheduler check point where HALT arrives, inside an instruction, and runs the rest of the instruction after HALT is released. The MC6809E data sheet (Motorola, HALT pin description) has the processor stop at the end of the current instruction, as ours does without mameCompat (js/machines/sam.js haltChanged, js/machines/coco3.js fireEvent, js/cpu/cpu6809.js haltTail).
  • CoCo 3 exact time (the disk drives' clock): MAME's machine time is reckoned in its 6809's cycles (1e18 / 894886 attoseconds, a GIME clock being a quarter of one at 0.89 MHz) and starts one CPU cycle later than ours; measured with a Lua tap on the WD1773's registers (its first status read at 0.272549799639 s, 7 CPU cycles after MAME's CoCo on the same firmware). Without mameCompat the GIME clock of the real 28.636363 MHz crystal is used (js/machines/coco3.js).
  • m6809 SYNC with an interrupt already pending takes 3 cycles in MAME (base6x09.lst), 5 in ours: the Motorola MC6809 data sheet's instruction table gives SYNC ">= 4" cycles, plus one to release (js/cpu/cpu6809.js; both paths tested in tests/cpu.test.js).
  • CoCo 3, a write to the SAM rate bits ($FFD6-$FFD9) from outside the CPU while the disk controller's HALT holds an instruction: MAME 0.264 carries the held instruction on at the new clock once HALT is released. Ours drops it (js/machines/coco3.js writeIO, haltCancel): the project's rule for any change from outside while an instruction is held (the MC6809E data sheet's HALT description: an outside change meets the CPU between instructions; see haltCancel), so its halted time is charged at the rate before the write and it runs again from its start, its bus accesses before the held one made again, at the new rate. Only the debugger's memory write reaches this (a program's own write is made by the instruction in flight, and a tool's poke skips the I/O page), so no firmware can observe it and the MAME comparisons do not cover it; tests/halt-held.test.js does.
  • Dragon 200-E: MAME's driver drives the VDG's INTEXT from two places, from each fetched byte (sam_read(), /D7) and from PB4 on every PIA1 port B write (coco12_state::pia1_pb_changed(), inherited). When they disagree, the write is a mode change to MAME's mc6847 and splits the line, so its reads run on past the visible area and, at SAM V=1, move the display counter, although nothing on the 200-E's VDG changed. The 200-E's PB4 reaches only the character generator (dragon200e_state::char_rom_r() in the same driver), so without mameCompat a PB write that changes no VDG input changes nothing (js/machines/sam.js mameIntextTrack; both halves tested in tests/models.test.js, raster case 11).
  • MAME's mc6847 records a line lazily: only on a mode change and at the next HS. The part of a line after a change is drawn from the last sample's mode, and pixels it never draws keep the previous frame's (MC6847.endLine, keepTail).
  • MC-10: MAME's CPU clock is a whole number of Hz (894887 against the VDG's 3579545 / 4), its 6801 core performs accesses at the instruction's start, the HS start is truncated one clock early, and a write before that start freezes the rest of the line (js/machines/mc10.js).
